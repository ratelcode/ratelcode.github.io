> SmolVLA를 SO-101 실물 로봇에 올리면서 겪은 튜닝 과정을 정리한 시리즈입니다 (9/9). 측정·커밋으로 확인한 내용과 제 의견을 문장에서 구분해 적었습니다.

> **용어 1줄 정리**
> - **정책(policy)**: 카메라·관절 상태를 입력받아 다음 동작(action)을 내놓는 학습된 모델입니다. 여기서는 SmolVLA를 말합니다.
> - **grasp pose**: 큐브를 집는 그 순간의 팔 전체 관절 자세입니다.
> - **shoulder_pan**: 6관절 중 1번 관절입니다. 팔을 좌우로 회전(azimuth)시키는 base 관절로, 큐브의 좌/우를 가르는 유일한 축입니다.
> - **RTC**: 액션 청크(한 번 추론에 50스텝)를 비동기로 갈아끼우는 추론 구조입니다. 8편에서 다뤘습니다.

---

## TL;DR

- 추론(RTC 비동기)이 부드럽고 빠르게 성공한 직후에도, gripper가 큐브 중앙이 아니라 항상 같은 방향(오른쪽 옆)으로 빗나가 큐브의 한쪽 옆을 집으려 했습니다. 무작위가 아니라 방향이 일관(systematic)됐다는 점이 첫 단서였습니다.
- 원인은 추론 코드도 캘리브도 아니었습니다. 수집 데이터(`so101_cube_v0`, 51 에피소드)의 큐브 위치 다양성이 사실상 0이었습니다. 좌우를 가르는 관절 `shoulder_pan`의 grasp 시점 값이, 데이터셋 전체 가동 범위(약 71°) 중 8° 폭 한 점에만 몰려 있었습니다.
- 위치 다양성이 0이면 정책은 "큐브를 보고 따라가기"를 배울 필요 없이 고정된 grasp pose를 암기합니다. 그래서 배포 때도 항상 외운 azimuth(≈ −22°)로 가고, 큐브가 그 자리에서 조금만 벗어나면 한쪽 옆에 떨어졌습니다.
- 대응은 세 갈래였습니다. 진단 도구 `demo_replay_rerun.py`로 grasp 구간을 자동 검출·시각화하고, 재발방지 게이트 `dataset_gate.py`에 `@check("grasp_pose_diversity")`를 추가했으며, 큐브를 워크스페이스 전역에 분산해 재수집하기로 했습니다.
- 전후 핵심 숫자: grasp pose 분산 중앙값 `arm_pose_spread_median`이 **0.059**(게이트 WARN)였고, 목표는 ≥0.12 PASS입니다.

## 1. 증상 — 무엇이 안 됐나

이 시리즈 앞부분에서 SmolVLA 정책을 SO-101 로봇팔에 올려 픽앤플레이스를 시키는 작업을 다뤘습니다. 8편까지 추론 파이프라인(액션 청크를 비동기로 갈아끼우는 RTC 구조)을 다듬어 rollout이 부드럽고 빠르게(큐가 비는 일 `queue_starved=0`) 돌게 만들었습니다. 동작은 매끄러운데 막상 결과를 보면 이상했습니다.

gripper가 큐브 중앙이 아니라 오른쪽 옆을 집으려 했습니다. 한두 번이 아니라 반복적으로, 그리고 방향이 항상 같았습니다. 이게 핵심 단서였습니다. 빗나감이 무작위라면 노이즈를 의심하겠지만, 방향이 한쪽으로 일관되게(systematic) 치우치면 그건 어딘가의 편향이 그림자를 드리운 것입니다.

또 하나 헷갈리게 한 점은, offline 지표는 좋았다는 것입니다. 학습 데이터에 대한 잔차(residual)나 분포 이탈(oos) 같은 수치는 멀쩡했습니다. 그런데 온라인에서 물체 위치가 학습 분포를 조금만 벗어나면 빗나갔습니다.

제 생각에는 "동작은 멀쩡한데 결과만 한쪽으로 치우친다"가 보이면, 추론 속도나 부드러움 문제는 이미 아닌 경우가 많습니다. 부드러움과 정확함은 다른 축이라고 봅니다.

## 2. 원인 — 왜 그랬나

먼저 무엇이 아닌지부터 박았습니다. 진단의 절반은 여기서 갈렸습니다.

배제한 원인은 두 가지입니다. 하나는 캘리브레이션입니다. follower 캘리브 파일(2026-06-11)이 수집(2026-06-20)과 현재 배포를 공통으로 덮습니다. 수집할 때와 배포할 때 같은 파일을 쓰므로, 좌우 오프셋이 거기서 생길 수 없습니다. 다른 하나는 추론 코드입니다. 8편의 RTC 최적화는 액션 청크의 좌표계·지연·큐 문제였고 grasp 위치와는 무관합니다. rollout은 `queue_starved=0`으로 정상 동작했습니다.

그럼 남는 건 데이터입니다. 좌우를 가르는 관절은 `shoulder_pan`(id 1, base azimuth) 하나뿐입니다. 전 51 에피소드의 grasp 시점 `shoulder_pan` 값을 집계했습니다.

grasp 시점 shoulder_pan 분포는 다음과 같았습니다.
```
mean -21.9°   std 4.2°   min -26.0°   max +6.1°
→ 50/51 grasp가 -26~-18° (8° 폭) 한 점에 몰림
→ 데이터셋 pan 전체 가동 범위는 -40~+32° (약 71°)
```

좌우를 가르는 유일한 관절이 grasp 순간 거의 한 값에 박혀 있었습니다. 51개 grasp 중 50개가 8° 폭 안에 들어왔고, 이는 데이터셋 pan 전체 범위(약 71°)의 작은 일부(원노트 표기 약 8%)에 불과합니다. 이걸 다른 위치 관절들로 확장해도 마찬가지였습니다. grasp 이벤트 시점의 pose 분산(각 관절 std ÷ range)의 중앙값이 0.059로, 관절들이 각자 전체 가동 범위의 4~9%만 움직인 셈입니다.

정리하자면 51개 데모를 한 세션에서 큐브를 거의 같은 자리에 두고 수집한 것입니다. grasp 순간 팔 전체가 매번 거의 같은 pose였고, 위치 다양성이 사실상 없었습니다.

![수집 위치가 한 곳에 몰린 경우와 전역 분산 비교](/diagrams/09_grasp_diversity.svg)

*왼쪽은 큐브를 거의 같은 칸에서만 모은 경우(분산 0.059·WARN)이고, 오른쪽은 격자 전역에 고루 흩어 모으는 재수집 목표(분산 ≥0.12·PASS)입니다.*

쉽게 말하면, 큐브가 늘 같은 자리에 있으면 정책은 카메라로 위치를 확인할 이유가 사라집니다. "팔을 외운 한 자세로 보내 닫기"만 반복해도 학습 데이터가 전부 맞아떨어지기 때문에, 위치를 따라가는 능력 대신 고정된 grasp 자세를 통째로 외워 버립니다. 그래서 배포 때 큐브를 새 자리에 놓으면 외운 자리로만 가서 한쪽 옆을 잡게 됩니다.

### 메커니즘 — 암기 vs 시각추종

여기서부터는 제 추론입니다. 위치 다양성이 0이면 정책은 "큐브를 카메라로 보고 그쪽으로 따라가는 것(시각추종)"을 배울 필요가 없습니다. "pan ≈ −22°로 가서 닫는다"는 거의 고정된 grasp pose 하나만 암기하면 학습 데이터를 전부 맞추기 때문입니다. 학습 손실 입장에서는 암기가 완벽한 정답인 셈입니다.

그래서 배포 때도 정책은 항상 외운 azimuth(≈ −22°)로 갑니다. 큐브를 학습 spot에서 조금만 다르게 놓으면, gripper는 여전히 −22°로 가서 큐브의 한쪽 옆에 떨어집니다. 큐브가 −22°보다 home(+) 쪽에 있으면 gripper가 큐브의 먼 쪽(=오른쪽)을 뭅니다. 방향이 항상 같은 이유가 여기 있다고 봅니다. 고정 azimuth를 노리니 큐브가 어느 쪽으로 벗어나든 grasp가 일관되게 반대쪽 옆에 떨어지는 것입니다.

offline 지표가 좋았던 것도 이 메커니즘으로 설명됩니다. 학습 분포 안에서는 암기가 정답이라 잔차가 작게 나옵니다. 실패는 분포 밖, 즉 큐브를 새 위치에 놓는 온라인에서만 드러납니다. 일반화는 원래 분포 밖에서만 검증되니까요.

## 3. 무엇을 바꿨나

두 갈래로 대응했습니다. 이번 원인을 확정할 진단 도구, 그리고 다음 수집에서 재발을 막을 게이트입니다. 커밋은 `a3521b1`입니다.

### (a) 진단 도구 — `demo_replay_rerun.py`

데모 데이터셋을 rerun `.rrd`로 재생하되, pick 구간만 자동으로 잘라 봅니다. 핵심은 gripper 신호(action idx 5)로 pick 이벤트를 검출하는 부분입니다.

- gripper 개폐 시퀀스로 pick 구간을 찾습니다. 접근하며 첫 열림 봉우리(first_open, 테이블 위 호버)가 나온 뒤 닫힘(grasp)으로 이어지는 흐름입니다. 코드는 열림 임계 `lo + 0.6·(hi−lo)`, 닫힘 임계 `lo + 0.35·(hi−lo)`로 검출합니다.
- 함정이 하나 있습니다. gripper가 가장 크게 벌어지는 글로벌 argmax는 트레이에 놓을 때(release)입니다. 그걸 grasp로 잡으면 안 되므로 first_open 이후의 첫 닫힘만 grasp로 잡아 명시적으로 회피합니다.
- 검출한 구간만 양 카메라(top/wrist)와 `shoulder_pan`/`gripper` 트레이스로 로깅하고, grasp 프레임에 event 마커를 찍습니다. top 카메라에는 `draw_guides`로 세로 중심선(노랑)과 1/3 보조선을 합성해 "사람이 큐브 중앙을 잡는지 옆을 잡는지"를 육안으로 판정합니다.

작은 큐브(2cm)가 얕은 카메라각에서 gripper에 가려져 정적 프레임 추출이 번번이 실패했는데, 동작 맥락(이벤트)으로 우회한 것이 이 도구의 요점입니다.

### (b) 재발방지 게이트 — `dataset_gate.py`의 `@check("grasp_pose_diversity")`

데이터셋을 학습에 넘기기 전에 자동 검사하는 게이트에 체크를 하나 추가했습니다. 관절명·DoF를 `info.json`에서 읽어 하드코딩 없이 동작하는 게 설계 원칙입니다.

```python
@check("grasp_pose_diversity")
def c_grasp_div(ctx):
    # gripper 관절을 히스토그램 양끝질량(end_mass)으로 자동 검출
    # — 어느 관절이 개폐인지 안다고 가정 안 함
    masses = [end_mass(k) for k in range(A_all.shape[1])]
    grip_j = int(np.argmax(masses))
    if masses[grip_j] < GATE["grasp_event_endmass"]:   # = 0.45
        yield _f("PASS", "뚜렷한 개폐 이벤트 없음 — 검사 N/A(비파지 태스크)")
        return
    # ... 에피소드별 grasp 프레임에서 위치 관절 pose를 모음 ...
    med = float(np.median(arm))   # = arm_pose_spread_median
    if med < GATE["grasp_spread_warn"]:                # = 0.12
        yield _f("WARN", "고정 grasp pose 암기 → 변동 위치서 빗나감, "
                         "워크스페이스 전역 분산 재수집 권장", arm_pose_spread_median=med)
    else:
        yield _f("PASS", "물체 위치 다양성 충분", arm_pose_spread_median=med)
```

위는 핵심 구조만 발췌한 형태입니다. 임계값과 분기 로직은 소스와 일치하되 전체 함수는 아닙니다.

설계 의도는 이렇습니다.

- WARN까지만 두고 FAIL은 하지 않습니다. 고정 위치 태스크에서는 낮은 grasp 다양성이 정상입니다. FAIL로 막으면 과탐(false alarm)이 되니, 막을지 말지는 사람이 판단하게 했습니다.
- 개폐 신호가 뚜렷할 때만 동작합니다. 양끝질량 `end_mass`(값이 히스토그램 양 극단 bin에 몰리는 정도)가 0.45 미만이면 gripper 2-state 신호가 불명확하다고 보고 N/A로 skip합니다. 파지가 없는 태스크에는 적용되지 않도록 한 것이라, 게이트가 form-factor를 가정하지 않습니다.
- grasp 이벤트가 검출된 에피소드가 3개 미만이면 그것도 WARN으로 처리합니다.

### (c) 해결 방향 — 재수집

큐브를 워크스페이스 전역에 분산해서 재수집합니다. 좌/중/우 × 근/원으로, 약 5cm 격자(~25×20cm)에 매 에피소드 다른 칸을 무작위 배치하는 방식입니다. 학습을 진행하는 조건은 재수집 후 게이트의 `arm_pose_spread_median`이 ≥0.12 (PASS, 이상 ≥0.20)가 되는 것입니다.

## 4. 전후 비교

| 지표 | before (cube_v0) | after (재수집 목표) |
|---|---|---|
| grasp 시점 shoulder_pan (mean ± std) | **−21.9° ± 4.2°** (min −26.0, max +6.1) | 워크스페이스 전역 분산 (수치 미측정) |
| grasp가 몰린 폭 / 전체 가동 범위 | **8° 폭 한 점 (50/51 grasp) / 전체 71°** | 좌/중/우 × 근/원 분산 목표 |
| grasp pose 분산 중앙값 `arm_pose_spread_median` | **0.059** (게이트 WARN) | **≥0.12 PASS**, 이상 ≥0.20 |
| `dataset_gate` grasp_pose_diversity 판정 | **WARN** @ 0.059 < 0.12 | 재수집 후 **PASS**가 학습 진행 조건 |

정량으로 확정된 것은 분포 수치(−21.9° ± 4.2°, 분산 0.059)와 배제된 원인(캘리브·추론 코드)입니다. "오른쪽으로 빗나감 → 고정 azimuth 암기"라는 인과는 추론이며 원노트에 의견으로 라벨돼 있습니다. 재수집 후의 실제 PASS 수치, 온라인 빗나감의 정량(오프셋 거리/실패율)은 아직 미측정이고 육안 관찰만 기록됐습니다. 또 "배포 시 카메라가 움직여 큐브가 학습 spot과 어긋났을" 또 다른 경로도 완전히 배제하지는 못했는데, 어느 쪽이든 해법은 데이터라는 결론은 같습니다. 참고로 grasp가 쓴 범위 비율은 원노트 §3에 "약 8%", 커밋·게이트 주석에 "약 6%"로 다르게 표기돼 있어, 본문에서는 단정값 대신 "8° 폭 한 점"으로만 적었습니다.

## 5. 회사에 적용한다면

로봇이 아니어도, 학습 데이터로 정책/모델을 돌리는 어떤 파이프라인에도 옮길 수 있는 체크포인트입니다.

1. 온라인에서 방향이 일관된(systematic) 편향은 노이즈가 아니라 데이터 분포의 그림자입니다. 추론 코드나 후처리를 먼저 만지지 말고, 수집 다양성부터 집계하는 게 좋습니다. 특히 모델이 실제로 결정을 내리는 시점(여기서는 grasp 순간)의 입력 위치 다양성을 봐야 합니다.

2. offline 지표가 좋아도 안심하면 안 됩니다. 입력 다양성이 0이면 모델은 입력을 보고 일반화하는 대신 고정된 출력을 암기합니다. 학습 분포 안에서는 암기가 정답이라 지표가 좋게 나옵니다. 일반화는 분포 밖에서만 검증되니, 새 위치·새 조건에서 따로 테스트해야 보입니다.

3. 정적 분석이 막히면 이벤트로 우회하면 됩니다. 여기서는 작은 물체와 얕은 카메라각 때문에 grasp 순간 프레임을 그림으로 뽑는 게 번번이 실패했습니다. 대신 gripper 개폐 이벤트로 그 시점의 pose만 골라 통계를 냈더니 빠르게 원인이 나왔습니다. 일반 ML로 치면, 전체 입력을 다 보지 말고 결정적 순간의 입력 분포만 떼어 집계하는 것입니다.

4. 한 번 발견한 실패 유형은 게이트에 굳혀 두는 게 좋습니다. 진단으로 끝내면 다음에 또 당합니다. `@check` 하나를 데이터 게이트에 추가해 다음 수집을 자동 검증하게 만들면, 1회성 디버깅이 재사용 가능한 자산이 됩니다. 단 막는 강도는 신중히 정해야 합니다. 정상적으로 낮은 다양성이 맞는 태스크(고정 위치 작업)도 있으니, FAIL이 아닌 WARN으로 두고 최종 판단은 사람에게 남깁니다.
