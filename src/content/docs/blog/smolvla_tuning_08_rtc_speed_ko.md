> SmolVLA를 SO-101 실물 로봇에 올리면서 겪은 튜닝 과정을 정리한 시리즈입니다 (8/9). 측정·커밋으로 확인한 내용과 제 의견을 문장에서 구분해 적었습니다.

## TL;DR

- 비동기 추론(RTC)을 켜니 동작은 매끄러워졌는데, 궤적 진행이 데모보다 눈에 띄게 느렸습니다.
- 원인은 세 가지였습니다. 첫째, 제어 주기가 `CONTROL_HZ=15`인데 데이터셋은 `fps=30`이라 정확히 절반속도로 재생됐습니다. 둘째, RTC 추론이 동기 추론보다 무거운데 큐와 지연을 너무 작게 잡았습니다. 셋째, `real_delay`를 잘못된 시점에 측정해 항상 0이 되던 잠복 버그가 있었습니다.
- 제어 주기, 지연, 큐 임계, 안전 클램프를 데이터셋 fps와 런타임 실측 지연이라는 두 입력에서 파생하도록 다시 설계해 풀었습니다.
- 전후로 바뀐 핵심 숫자만 추리면, 재생 속도가 0.5x에서 1.0x(native)로, 기본 24Hz 기준 1.6x가 됐고, `queue_starved_steps`는 0, `measured_delays`는 죽은 0열에서 실값(~5–6)으로, `pred_ms_p95`는 부트스트랩 가정 450에서 실측 **251ms**로 바뀌었습니다.

---

## 1. 증상 — 무엇이 안 됐나

이 시리즈의 앞 글에서 다룬 RTC(Real-Time Chunking, 실시간 청킹)는 다음 액션 묶음(chunk)을 백그라운드 스레드가 미리 만들어 두고, 메인 루프는 큐에서 액션을 하나씩 꺼내 쓰는 비동기 추론 구조입니다. 배경만 짧게 짚으면, 시퀀스 정책은 한 번의 추론으로 미래 50스텝 분량의 액션을 한꺼번에 내놓습니다(`predict_action_chunk`). 동기 방식은 한 묶음을 다 쓰고 나서 다음 묶음을 추론하므로, 그 추론 시간 동안 로봇이 멈칫(stutter)합니다. RTC는 다음 묶음을 미리 만들어 두어 이 멈칫을 없앱니다.

RTC를 켠 결과는 반은 성공이었습니다.

- 성공한 쪽은 청크 경계의 멈칫이 사라져 동작이 매끄러워진 점입니다.
- 실패한 쪽은 전체 궤적 진행이 시연(demo)보다 눈에 띄게 느렸다는 점입니다. 사용자 요청은 단순했습니다. "속도 좀 더 빠르게."

부드러움은 native 궤적(실제 기록된 데모 궤적)을 그대로 재생했기 때문이고, 느림은 그 궤적을 너무 천천히 소비했기 때문입니다. 두 현상이 같은 원인에서 나왔다는 게 이 글에서 하고 싶은 이야기입니다.

---

## 2. 원인 — 왜 그랬나

### 원인 1: 제어 Hz가 기록 fps의 절반 (절반속도 버그)

시퀀스 정책의 액션 청크는 시간축을 자르지 않고 50스텝 전체를 반환합니다(`predict_action_chunk`). 그리고 큐(`ActionQueue.get()`)는 한 번 호출할 때 액션 1개를 꺼내고 인덱스를 +1 합니다. 즉 "제어 한 스텝 = 액션 한 개 소비"가 성립합니다.

여기서 조용한 함정이 나옵니다. 제어 카데시(주기)가 곧 재생 속도라는 점입니다.

데이터셋 `so101_cube_v0`는 30fps로 기록됐습니다. 따라서 50-pose 청크의 각 pose는 데모에서 `1/30s ≈ 33.3ms` 간격의 미래 목표입니다. 그런데 rollout은 `CONTROL_HZ=15`(66.7ms/step)로 한 스텝에 한 pose씩 발행했습니다. 같은 궤적을 두 배 시간에 재생한 셈이고, 정확히 절반속도(0.5x)가 된 것입니다.

이건 외삽이나 모델 오류가 아닙니다. 정책이 내놓은 궤적은 정확했고, 단지 소비 속도가 절반이었을 뿐입니다.

![제어 Hz와 데이터셋 fps 불일치로 생기는 절반속도](/diagrams/08_rtc_speed.svg)

*캡션: 같은 청크를 제어 Hz만 바꿔 소비할 때, 한 청크를 다 쓰는 데 걸리는 시간(가로 길이)이 곧 재생 속도다. 15Hz는 native가 끝나는 시점에 절반(pose 3)밖에 못 가서 0.5x, 30Hz=fps면 같은 시점에 끝나 1.0x native가 된다.*

쉽게 말하면, 청크 안의 pose들은 데모에서 33.3ms 간격으로 찍힌 "목표 좌표"이고, 제어 한 스텝마다 그 좌표를 하나씩 내보냅니다. 제어 주기가 66.7ms(15Hz)면 한 좌표를 두 배 오래 들고 있는 셈이라 똑같은 길을 두 배 시간에 걷게 됩니다. 그래서 Hz가 절반이면 속도도 정확히 절반이 됩니다.

### 원인 2: RTC 추론이 동기 추론보다 무겁다 → 지연을 과소 설계

RTC 가이드는 매 denoise(노이즈 제거) step마다 forward뿐 아니라 backward까지 돕니다(`torch.autograd.grad`로 보정항 계산, `modeling_rtc.py`). flow-matching 루프가 step마다 이걸 반복하므로, 실측 추론 시간이 오프라인 단순 `predict`보다 무겁습니다.

원노트(`m7w4_rtc_async_efficiency.md`)는 오프라인 `predict` 베이스라인을 285ms로, RTC-on 실측을 "약 2배"로 서술합니다. 다만 이 두 값을 같은 실행 안에서 직접 비교한 수치는 rollout JSON에 남아 있지 않습니다. JSON에는 실측 `pred_ms_p95=251ms`만 출력됩니다. 그래서 "약 2배"는 노트의 서술로 받아들이면 됩니다.

문제는 그 결과입니다. 동기 rollout의 지연 직관(오프라인 predict 시간)으로 정적 delay를 잡으면, 실측이 더 무거워서 큐와 지연이 과소 설계됩니다. 그러면 새 청크가 이미 지나간 prefix를 다시 실행해 경계에서 후진-stutter가 생길 위험이 있습니다.

### 원인 3: `real_delay`가 항상 0이 되던 잠복 버그

`real_delay`는 추론이 도는 동안 메인 루프가 실제로 소비한 액션 수입니다. 이 값을 알아야 새 청크에서 이미 지나간 prefix를 정확히 폐기할 수 있습니다.

그런데 예측 스레드가 이 값을 `merge` 후에 읽고 있었습니다. `merge`는 큐 내부 인덱스를 0으로 리셋합니다(`action_queue.py`). 리셋 뒤에 소비량을 재면 당연히 항상 0이 나옵니다.

그래서 `measured_delays`는 의미 없는 0열이었고, merge는 매번 정적 fallback 값만 받았습니다. 높은 Hz에서는 이미 지나간 액션을 0개로 폐기 처리하고, 그걸 다시 실행하는 후진-stutter로 이어질 수 있습니다.

## 3. 무엇을 바꿨나

이번 재설계의 기준은 하나였습니다. 카데시, 지연, 큐 임계, 안전 클램프를 전부 두 입력(데이터셋 fps와 런타임 실측 지연)에서 파생시키는 것입니다. 상수로 박지 않으면 "절반속도" 부류의 버그가 구조적으로 재발하지 못합니다. 관련 파일은 `workbench/so101/scripts/svla_rollout_rtc.py`입니다.

먼저 제어 Hz를 fps에서 파생하도록 했습니다. 과거의 상수 `CONTROL_HZ=15`를 제거하고 데이터셋 fps에서 파생합니다. 기본은 보수적으로 24Hz(현행 대비 1.6x), env로 30Hz(=fps, 1.0x native)까지 올릴 수 있습니다.

```python
DS_FPS = int(json.load(open(_DS_DIR / "meta/info.json")).get("fps", 30))
# 카데시 = 데이터셋 native fps. 같은 fps로 소비해야 1.0x 재생.
# (과거 CONTROL_HZ=15는 30fps 데모를 0.5x로 재생한 버그.)
CONTROL_HZ = int(os.environ.get("CONTROL_HZ", "24"))
```

다음으로 지연을 실측 p95로 자가보정하게 했습니다. 정적 `RTC_DELAY` 대신 런타임에서 추론 시간 p95(`pred_p95`)를 추적해 지연을 계산합니다. 부트스트랩 초기값만 추정(env `PRED_MS`, 기본 450)으로 잡고, 이후엔 실측이 끌고 갑니다. 큐 고갈을 막기 위해 refill 임계는 `drain_p95 + EXEC_HORIZON`으로 둡니다.

```python
def derive_delay(pred_ms: float, hz: float) -> int:
    # 추론 중 소비되는 액션 수 + 여유 1
    return math.ceil(pred_ms / 1000.0 * hz) + 1
```

`real_delay` 버그는 소비량을 `merge` 전에 측정해 그대로 넘기는 방식으로 고쳤습니다.

```python
# merge가 last_index를 0으로 리셋하기 전에 읽어야 함 (과거엔 merge 후 읽어 항상 0이었음)
consumed = 0 if first else max(0, queue.get_action_index() - idx_at_start)
queue.merge(norm_chunk, norm_chunk, real_delay=consumed,
            action_index_before_inference=(None if first else idx_at_start))
```

마지막으로 안전 클램프를 각속도(deg/s)에서 파생하도록 바꿨습니다. per-step 클램프 값을 `MAX_VEL_DPS / CONTROL_HZ`로 계산합니다. 속도천장 120°/s는 불변이라, Hz를 올려도 안전이 완화되지 않습니다(per-step을 고정값으로 두면 Hz가 두 배가 될 때 deg/s도 두 배가 됩니다). 이번 24Hz 실행에서는 `120 / 24 = 5.0°/step`으로 잡혔습니다.

이외에 부수적으로 정리한 것들이 있습니다. CPU 역정규화와 이미지 로깅을 약 10Hz로 스로틀(`IMG_LOG_EVERY`)해 제어 스레드의 critical-path를 비웠고, footgun이던 `policy.reset()`을 제거했으며, `NUM_STEPS` knob을 노출했습니다.

안전 감시 빈도는 일부러 손대지 않았습니다. 리뷰는 과부하 감시용 `Present_Load` 읽기를 매 스텝에서 N스텝마다로 줄이라고 제안했지만, 그 읽기가 "파손 신호 시 즉시 중단"의 감시선이라 반응 시간을 성능과 거래할 수 없다고 봅니다. critical-path 여유는 안전 비용이 0인 곳(jpeg 압축, CPU 역정규화)에서만 회수했습니다.

## 4. 전후 비교

모든 "after" 숫자는 24Hz 40초 실기 1회(`smolvla_rollout_rtc_so101_ft_v0.json`)와 학습노트에서 가져왔습니다.

| 지표 | Before | After |
|---|---|---|
| 재생 속도 배수 | 0.5x (`CONTROL_HZ=15`, 30fps 데모 절반속도) | 1.0x native (Hz=fps); 기본 24Hz=1.6x |
| `queue_starved_steps` | 고갈 위험 (정적 refill) | 0 |
| `measured_delays` (real_delay) | 항상 0 (죽은 0열, merge 후 측정) | `[0, 6, 5, 6, 5, ...]` ~5–6 (42값, 실값화) |
| `pred_ms_p95` (RTC 추론 지연) | 부트스트랩 가정 450ms (정적) | 실측 251ms (자가보정) |
| `inference_delay_final` / `refill_threshold_final` | 정적 / 고정 | 8 / 25 (p95 자가보정 추적) |
| 안전 클램프 단위 | per-step 고정값 (Hz↑ 시 deg/s 완화) | `MAX_VEL_DPS/Hz` = 120°/s 불변 (24Hz→5.0°/step) |
| `last_pred_ms` / `chunks_predicted` / `steps_executed` | — | 242ms / 42 / 959 |
| 안전 종료 | — | `aborted=null`, `torque_off_verified=true` |

체감 결과는 "부드러움 유지에 빨라짐"이었고, 속도 목표를 24Hz 기본에서 달성했습니다. 멀티에이전트 리뷰는 4개 관점(카데시, 추론지연, critical-path, 큐)을 병렬로 돌려 26개 finding 중 25개를 채택했고(커밋 `f104447`), finding마다 lerobot 소스로 대조 검증했습니다. 이 과정에서 잘못된 finding 1건(가중치 방향 오독)은 기각했습니다.

## 5. 회사에 적용한다면

이 사례를 일반 ML/로봇 파이프라인으로 옮길 때 챙겨볼 체크포인트입니다. 여기는 제 의견입니다.

1. 시퀀스(action-chunk) 정책을 실기 재생할 때 제어 주기를 상수로 박지 않는 게 좋습니다. 재생 카데시가 곧 재생 속도이기 때문입니다. 제어 Hz와 기록 fps가 불일치하면 모델 오류가 아니라 조용한 속도 버그가 생깁니다. 카데시를 데이터셋 fps에서 파생하면 Hz=fps일 때 1.0x native가 됩니다.
2. 비동기 추론 파이프라인의 지연·큐 설계는 추정값이 아니라 런타임 실측 p95로 자가보정하는 편이 낫습니다. 특히 RTC처럼 매 step에 backward가 있는 무거운 추론은 동기 추론 직관보다 느려서, 정적 delay가 과소 설계되기 쉽습니다. 측정이 끌고 가게 두는 게 안전합니다.
3. 안전 불변량은 per-step이 아니라 per-second 단위로 묶는 게 좋습니다. 속도천장을 deg/s 같은 절대 단위로 두면, 제어 주기를 바꿔도 안전이 자동으로 완화되지 않습니다.
4. 멀티에이전트(다관점) 리뷰는 finding마다 소스 대조 검증을 동반해야 합니다. 검증을 붙이면 잠복 버그(merge 후 측정해 항상 0이던 것)와 그럴듯한 오답(가중치 방향 오독)을 한 번에 거를 수 있습니다. 검증 없는 리뷰는 설득력 있는 오답을 통과시키기 마련입니다.
5. 안전 감시 빈도는 최적화 대상에서 빼는 게 맞다고 봅니다. 과부하 즉시중단 같은 감시 read는 critical-path를 줄인다는 이유로 빈도를 낮추지 않습니다.

한 가지 덧붙이면, 30Hz(2x)로 더 가려면 실측 p95 251ms가 청크 가용량을 빡빡하게 만듭니다. 그래서 `NUM_STEPS`를 낮춰 추론을 먼저 줄여야 하고, 하드웨어에 올리기 전에 `compare_models`로 오프라인 fidelity(residual/oos)를 통과시키는 게 선행 조건이라고 봅니다. 참고로 이 rollout에서 grasp가 큐브 오른쪽으로 치우치는 별개 증상이 관찰됐는데, 이건 추론이나 속도가 아니라 데이터 다양성 문제로 판명돼 다음 글에서 다룹니다. RTC 속도 최적화 자체는 여기서 종결했습니다.
